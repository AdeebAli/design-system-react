# ADR 0001: Use vanilla-extract for styling

- **Status:** Accepted
- **Date:** 2026-11-01

## Context

`design-system-react` is a personal design system intended as the foundation
for all future projects (e.g., a personal site/blog and data-heavy tools such
as a fantasy football analysis app). It will be published as a package (npm or
GitHub Packages) and consumed by multiple independent projects.

Requirements that drive the styling choice:

- **Opinionated by default:** installing the package should produce a finished,
  cohesive UI with zero configuration.
- **Customizable:** consumers can override themes, tokens, and individual
  components.
- **Strong typing:** tokens, variants, and style props must be type-checked with
  full IntelliSense (e.g., `padding="4"` autocompletes the spacing scale).
- **Composable Box primitive:** every component is built on a `Box` that models
  the CSS box model and exposes typed, token-constrained style props.
- **Library distribution:** consumers should not need special build tooling to
  use the package.
- **Framework-agnostic rendering:** must work with Vite, Next.js, and React
  Server Components.

## Decision

Use [vanilla-extract](https://vanilla-extract.style/) as the styling layer:

- Tokens and themes are defined in TypeScript and compiled to CSS custom
  properties (`createThemeContract` / `createTheme`).
- The `Box` primitive's style props are generated with `@vanilla-extract/sprinkles`,
  producing a finite, typed set of atomic classes constrained to tokens.
- Component variants are defined with `@vanilla-extract/recipes`.
- All CSS is compiled at library build time. The package ships JS plus a static
  stylesheet; consumers import the stylesheet and need no bundler plugin.

## Alternatives considered

| Option | Why not chosen |
|---|---|
| **Tailwind CSS** | Class strings aren't type-checked; mapping typed Box props to classes is awkward; consumers must configure Tailwind; overrides depend on class order without `tailwind-merge`. |
| **CSS Modules + CSS variables** | No types for tokens or variants without hand-maintained declarations; Box style props would need inline styles or a large hand-written class set. |
| **Runtime CSS-in-JS** (Emotion, styled-components) | Runtime style generation costs performance; poor React Server Components support; ecosystem moving away (Chakra v3 left Emotion). |
| **Panda CSS** | Closest runner-up (typed tokens, recipes, inline style props). Rejected because CSS is generated by static extraction in the *consumer's* build: every consuming project must install and configure Panda, scan the library in `node_modules`, and keep generated `styled-system` code and Panda versions in sync with the library. That breaks "install and it works." |
| **StyleX** | Smaller ecosystem, required build integration, less ergonomic theming. |

## Consequences

**Positive**

- Zero runtime styling cost; compatible with React Server Components.
- Consumers install the package and import one stylesheet. No build plugin required.
- End-to-end type safety for tokens, themes, variants, and Box props.
- Theming via CSS variables lets consumers restyle without rebuilding the library.

**Negative / tradeoffs**

- Styles live in separate `.css.ts` files rather than inline in components.
- The library build requires a vanilla-extract bundler plugin (e.g., Vite/tsup/Rollup integration).
- Box style props accept only token values (e.g., `p="4"`, not `p="13px"`).
  Arbitrary values go through the `style` / `className` escape hatches. This is
  intentional: it enforces consistency with the system's opinions.
- Less flexible for values computed at runtime; dynamic values must use CSS
  variables (`@vanilla-extract/dynamic`) or inline styles.
- Consumers who want to write their own typed styles against the theme can
  optionally adopt vanilla-extract themselves, but it is not required.
